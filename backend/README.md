# Baluarte backend

FastAPI service and background worker for Baluarte. Requires Python 3.12+.

## Development

```sh
python3.12 -m venv .venv
. .venv/bin/activate
pip install -e '.[dev]'

uvicorn baluarte.main:app --reload   # http://127.0.0.1:8000/api/v1/health
pytest
ruff check . && ruff format --check .
mypy
```

The OpenAPI contract is generated by FastAPI at `/openapi.json`.

## Configuration

| Variable | Purpose |
|---|---|
| `BALUARTE_DATABASE_URL` | PostgreSQL URL without a password, e.g. `postgresql://baluarte@db:5432/baluarte?sslmode=require` |
| `BALUARTE_DATABASE_PASSWORD_FILE` | File containing the database password (mounted secret) |
| `BALUARTE_LOG_LEVEL` | `DEBUG`, `INFO` (default), `WARNING` or `ERROR` |
| `BALUARTE_LOG_FORMAT` | `json` (default, one object per line) or `text` |

Secrets are only read from files: every secret has a `*_FILE` variable, and setting the secret itself in the environment (for example `BALUARTE_DATABASE_PASSWORD`) is rejected. Invalid logging settings fall back to `INFO` and `json` and log an error. Logs are redacted as described in [docs/SECURITY.md](../docs/SECURITY.md#secrets-and-logs).

OIDC sign-in is off until `BALUARTE_PUBLIC_URL`, `BALUARTE_OIDC_ISSUER` and `BALUARTE_OIDC_CLIENT_ID` are all set; until then sign-in and every protected endpoint answer 503. Setting only some of them, or mapping no groups, is a configuration error (logged, and the same 503). See [ADR-0006](../docs/architecture/ADR-0006-server-side-oidc-sessions.md).

| Variable | Default | Purpose |
|---|---|---|
| `BALUARTE_PUBLIC_URL` | | Browser-facing origin, e.g. `https://baluarte.example.internal`. Must be https unless the host is loopback. The redirect URI to register with the provider is this plus `/api/v1/auth/callback` |
| `BALUARTE_OIDC_ISSUER` | | Issuer URL (https); discovery is read from `/.well-known/openid-configuration` |
| `BALUARTE_OIDC_CLIENT_ID` | | Client ID registered with the provider |
| `BALUARTE_OIDC_CLIENT_SECRET_FILE` | | File holding the client secret. Omit for a public client (PKCE only) |
| `BALUARTE_OIDC_SCOPES` | `openid profile email` | Requested scopes; must include `openid`. Add the scope your provider needs to release groups |
| `BALUARTE_OIDC_ROLES_CLAIM` | `groups` | Claim listing the user's groups. Read from the ID token, or from userinfo if the ID token lacks it |
| `BALUARTE_OIDC_ADMIN_GROUPS`, `BALUARTE_OIDC_ANALYST_GROUPS`, `BALUARTE_OIDC_AUDITOR_GROUPS` | | Comma-separated groups granted each role; matching is exact and case-sensitive |
| `BALUARTE_GITLAB_URL` | | https URL of the GitLab instance; unset means GitLab is not configured |
| `BALUARTE_GITLAB_TOKEN_FILE` | when the URL is set | File containing a `read_api` token |
| `BALUARTE_GITLAB_TIMEOUT_SECONDS` | | Per-request timeout, 1 to 120 (default 15) |
| `BALUARTE_GITLAB_SYNC_INTERVAL_MINUTES` | | Worker collection schedule, 15 to 10080 minutes (default 360), or `0` for on request only |
| `BALUARTE_SESSION_IDLE_MINUTES` | `60` | Session ends after this long without a request |
| `BALUARTE_SESSION_LIFETIME_MINUTES` | `480` | Session ends this long after sign-in regardless of activity |

To trust a private CA for the identity provider, point `SSL_CERT_FILE` at a CA bundle. Certificate verification cannot be disabled.

## Background worker

`baluarte-worker` runs background jobs (same image as the API, different command). It waits for the database and for migrations to reach head, then claims only the job kinds registered in `baluarte/jobs/handlers.py`, so an older worker leaves newer kinds queued during a rolling upgrade. SIGTERM finishes the current job, then exits. `baluarte-worker healthcheck` exits 0 while the worker's heartbeat file is fresh, for container probes. See [docs/DATA_MODEL.md](../docs/DATA_MODEL.md#jobs) for leasing and retries.

| Variable | Default | Purpose |
|---|---|---|
| `BALUARTE_WORKER_POLL_SECONDS` | `5` | Wait between polls when no job is due |
| `BALUARTE_WORKER_LEASE_SECONDS` | `300` | Lease length; renewed every third of this (at most every 30s) while a job runs |

Handlers take the claimed job and must be idempotent. Raise `JobError("safe message")` to retry or `PermanentJobError` to stop; the message is stored on the job and shown to admins, so it must not contain secrets.

## Endpoints

- `GET /api/v1/health`: liveness. Does not touch the database.
- `GET /api/v1/ready`: 200 when PostgreSQL is reachable and migrated, otherwise 503 with which check failed. Errors are logged, not returned.
- `GET /api/v1/auth/login?return_to=/path`: redirects to the identity provider. `return_to` must be a same-origin path.
- `GET /api/v1/auth/callback`: the provider's redirect target. Sets the session cookie and redirects to `return_to`, or to `/sign-in?error=<code>` (`expired`, `provider_denied`, `provider_unavailable`, `not_authorized`, `sign_in_failed`).
- `GET /api/v1/auth/me`: the signed-in user, roles, permissions, session expiry and CSRF token; 401 without a session.
- `POST /api/v1/auth/logout`: revokes the session; needs the `X-CSRF-Token` header.

- `GET /api/v1/jobs?state=&kind=&limit=&before_id=`: jobs newest first, without payloads; `next_before_id` pages backwards. Needs `jobs:read` (admin).
- `GET /api/v1/audit-events?action=&actor=&since=&until=&limit=&before_id=`: audit events newest first with their `details_digest`; `since`/`until` need a time zone. Needs `audit_log:read` (admin, auditor).
- `GET /api/v1/settings`: effective logging, database, GitLab and authentication settings; secrets appear only as `configured` or `not_set`. Needs `settings:manage` (admin).
- `GET /api/v1/gitlab/instance`: configured URL, version, edition, the latest capability snapshot and whether it is `stale` (older than 24 hours or never run). Needs `inventory:read` (every role).
- `POST /api/v1/gitlab/capabilities/refresh`: queues capability detection in the worker; returns 202 with `job_id`, and requests in the same minute share one job. 409 when GitLab is not configured. Needs `settings:manage` (admin) and the CSRF header.
- `GET /api/v1/gitlab/freshness`: per-kind collection status (`failed`, `never`, `stale`, `partial`, `fresh`), the latest run of each kind, and resource counts by state and with errors. Needs `inventory:read` (every role).
- `GET /api/v1/gitlab/projects/{gitlab_id}/observations`, `GET /api/v1/gitlab/groups/{gitlab_id}/observations` and `GET /api/v1/gitlab/instance/observations` (`?limit=&before_id=`): observation-time evidence newest first, with source, collection run and job, payload, `payload_digest` and `digest_valid`; 404 for a project or group not in the inventory. Need `evidence:read` (every role). See [docs/AUDIT_EVIDENCE.md](../docs/AUDIT_EVIDENCE.md#observations).
- `GET /api/v1/gitlab/runs?kind=&status=&limit=&before_id=`: collection run history, newest first. Needs `inventory:read`.
- `GET /api/v1/gitlab/groups?state=&search=&parent_gitlab_id=&has_error=&limit=&after_id=`: discovered groups and subgroups in ID order; `search` matches `full_path` case-insensitively; `next_after_id` pages forwards. Needs `inventory:read` (every role).
- `GET /api/v1/gitlab/projects?state=&search=&namespace_gitlab_id=&namespace_kind=&visibility=&archived=&has_error=&limit=&after_id=`: discovered projects, archived ones included, in ID order; `search` matches `path_with_namespace` case-insensitively; `namespace_kind` is `group`, `user` (personal) or null when not yet known. Needs `inventory:read` (every role).
- `POST /api/v1/gitlab/projects/discover`: queues project discovery; same behaviour as group discovery. Needs `settings:manage` (admin) and the CSRF header.
- `POST /api/v1/gitlab/groups/discover`: queues group discovery in the worker; same 202, per-minute and 409 behaviour as the capability refresh. Needs `settings:manage` (admin) and the CSRF header.
- `POST /api/v1/gitlab/diagnostics`: tests the GitLab connection and token permissions (see [docs/GITLAB_INTEGRATION.md](../docs/GITLAB_INTEGRATION.md#diagnostics)). Returns 200 with a report whenever the checks ran, including failures; read `status`. Needs `settings:manage` (admin) and the CSRF header.
- `POST /api/v1/policies/validate`: validates `{"source_yaml": "..."}` against the baseline schema without saving; 200 with `valid` and `errors` (each with a `path` such as `spec.rules[1].allowed`). Needs `policy:write` (admin, analyst) and the CSRF header.
- `POST /api/v1/policies`: saves the source as the next immutable version of the policy named by `metadata.name`; 201 when created (audited as `policy.version_created`), 200 when identical to the latest version, 422 with `detail.errors` when invalid. Needs `policy:write` and the CSRF header.
- `GET /api/v1/policies`, `GET /api/v1/policies/{name}/versions?limit=` and `GET /api/v1/policies/{name}/versions/{version}`: policy names with their latest version, versions newest first, and one version with its exact source, digest and parsed document. Need `findings:read` (every role). See [docs/POLICY_ENGINE.md](../docs/POLICY_ENGINE.md).
- `POST /api/v1/policy-assignments`: pins `{"policy_name", "version", "target_type", "target_id"}` to the instance (no `target_id`), a group or a project (GitLab ID). Another version of the same policy on that target is replaced. 201 when assigned (audited as `policy.assigned`), 200 when already assigned, 404 for an unknown version or a target not in the inventory, 409 when GitLab is not configured or the target is missing or inaccessible. `DELETE /api/v1/policy-assignments/{id}` removes one (204, audited as `policy.unassigned`). A change queues an evaluation unless one is already waiting. Both need `policy:write` and the CSRF header.
- `GET /api/v1/policy-assignments?policy_name=&target_type=&target_id=&after_id=&limit=`: assignments with their version, digest and target path and state. Needs `findings:read`.
- `POST /api/v1/evaluations/run`: queues `policy.evaluate`; 202 with `job_id`, requests in the same minute share one job, 409 when GitLab is not configured; audited as `policy.evaluation_requested`. Needs `policy:write` and the CSRF header. Evaluations are also queued after each project discovery and after a policy assignment changes.
- `GET /api/v1/findings?state=&outcome=&severity=&project=&policy=&rule=&after_id=&limit=`: findings with their latest evaluation, in ID order; `outcome` filters on the latest outcome. `GET /api/v1/findings/{id}` and `GET /api/v1/findings/{id}/evaluations?before_id=&limit=` (every evaluation of that rule for that project, newest first, across versions). Need `findings:read`.
- `GET /api/v1/gitlab/projects/{gitlab_id}/evaluations`: the latest result of each rule in force, from the project's latest evaluation; empty when the latest successful run gave it none. Needs `findings:read`.
- `GET /api/v1/evaluations/freshness`: `failed`, `never`, `stale`, `fresh` or `not_configured`, with `running`, `queued`, `behind_collection` (a project discovery finished after the latest successful evaluation started), the latest run and `last_success_at`. `GET /api/v1/evaluations/runs?before_id=&limit=`: run history. Need `findings:read`. See [docs/DATA_MODEL.md](../docs/DATA_MODEL.md#evaluations-and-findings).
- `GET /api/v1/gitlab/projects/{gitlab_id}/effective-policies` and `GET /api/v1/gitlab/groups/{gitlab_id}/effective-policies`: the policies in force, the resolution path, every assignment considered with its outcome (`effective`, `overridden`, `out_of_scope`), and `ancestry` (`complete` or `incomplete`, with `gaps`). Need `findings:read`.

Every other endpoint requires a session (401 without one) and is checked against the permission matrix in [docs/SECURITY.md](../docs/SECURITY.md).

## Database and migrations

```sh
baluarte-migrate                                   # wait for the database, then upgrade to head
alembic revision --autogenerate -m "describe change" --rev-id 0010
```

Review every autogenerated revision; triggers and data migrations must be written by hand. See [docs/DATA_MODEL.md](../docs/DATA_MODEL.md).

Database tests need a PostgreSQL server where the test user can create databases. Each test creates and drops its own database:

```sh
docker run -d --name baluarte-testdb -e POSTGRES_USER=baluarte -e POSTGRES_PASSWORD=devonly \
  -p 127.0.0.1:55432:5432 postgres:17-alpine
export BALUARTE_TEST_DATABASE_URL=postgresql://baluarte:devonly@127.0.0.1:55432/postgres
pytest
```

Without `BALUARTE_TEST_DATABASE_URL` the database tests are skipped; CI sets `BALUARTE_REQUIRE_DB_TESTS=1` so they fail instead.
